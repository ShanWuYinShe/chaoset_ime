# 拼音匹配与输入预测调优（本项目专用）

适用于 `engine/` 里与「输入串 → 候选列表」相关的任何改动（切分、匹配层级、
排序打分、续接预测）。核心原则：**先用数据量化，再改代码；改完必须前后对比**。

## 一、先建量化基线（不要凭感觉改排序）

### 1. 写一个只读扫描器

放在 `.workwork/verify/scan/main.go`（`.workwork/` 已 gitignore，不进仓库），
从仓库根目录 `go run ./.workwork/verify/scan` 即可 `import "chaoset.ime/engine"`
（**不要**在 `.workwork` 下建 go.mod，会破坏模块解析）。

口径（必须固定，否则前后不可比）：

- 词条池：`data/dict_common.tsv` 中 2–4 音节、词频 ≥30、且「词长(rune) == 音节数」
  的规则词条（约 3.6 万条）；
- **确定性采样**：按 (词, 拼音) 排序后每 25 条取 1 条（约 1,460 条）。
  绝不能用 map 遍历顺序采样——每次跑的词集不同，数字没有意义；
- 取全部候选用 `Session.NextPage()` 翻到底（每页 6 条）；
- rank 判定必须**同时匹配词与音节序列**（`c.Text == word && c.Syllables == key`），
  否则同形词的不同切分会被误判为命中；
- 全量扫描 14 万词条太慢（单次组词约 25–31µs，2026-10-29 复测；原口径约 20µs。高负载下会更高；且翻页取全部候选会放大开销），
  采样后单次约 10 秒可跑完。

场景定义（缺一不可，覆盖输入法的真实形态）：

| 场景 | 构造 | 为什么必须测 |
|---|---|---|
| `full` | 完整全拼 | 基准，必须不退化 |
| `tail1` | 去掉最后 1 个字母 | **最高频形态**：每个音节都必然经过「打了一半」 |
| `tail2` | 去掉最后 2 个字母 | 更早的中间态 |
| `initials` | 各音节首字母 | 简拼 |
| `mixed` | 首音节全拼 + 其余简拼 | 混拼 |

### 2. 拿基线：用 git stash 而不是另开目录

```sh
git stash push -- engine/                     # 暂时退回 main 的 engine
go run ./.workwork/verify/scan                # 记录基线数字
git stash pop                                 # 恢复改动
```

**注意**：`git stash pop` 后必须 `git status --short` 确认改动回来了。
另外扫描器本身不要放在被 stash 的路径下（放 `.workwork/` 正好安全）。

## 二、已经踩过的五个打分陷阱

### 陷阱 1：用户调频分被当成静态词频

`UserDict.Score` 返回的是「次数 × 500 × 时间衰减」，量级数千；静态词频只有 1–99。
整句 DP（`sentence.go`）里若直接 `entry.Freq * l`，用户学过的单字会被放大成
几千分霸榜，把完整词挤成碎字拼接（`wmd` 出「我没的」而不是「我们的」）。

正确做法：用户词条并入规划时压到固定基础分（`userEntryBaseFreq`），
真实权重交给 `user.Score` 的上下文加成分支单独计算。见 `mergeUserEntries`。

### 陷阱 2：续接预测反噬完整输入

末音节在输入串上**无法区分**「已打完」与「还差几个字母」：
`yisha` 既可能是 `yi'sha`（一霎，完整）也可能是 `yi'shang` 的前缀。
如果无条件把续接候选置于最高优先级，「一霎」会被高频的「以上」压掉，
全拼首选率直接掉 2.8 个百分点（实测 80.75% → 77.95%）。

正确做法：让两种解析**同层竞争**，由「词频 − penalty × 补全字符数」决出，
不做场景特判。penalty 用数据扫描定型（见下），只对「输入压根无法切成干净音节」
（`quanmia` → `quan'mi'a`）的情况让续接强制领跑。

### 陷阱 3：把「末段是完整音节」当成不需要预测

`zhonggu` 的末段 `gu` 本身是合法音节，直觉会认为「精确匹配已经够了」。
反例：按此直觉实现，只能出「中古」，「中国」永远不可达。
判据应是「该音节还能否延长（是否存在以它为前缀的更长音节）」，
不是「它本身合不合法」。见 `syllableContinuations`。

### 陷阱 4：形态判据必然误伤「手误 vs 合法混拼」

错拼修正（`zhogn` → 中）最容易写错的地方，是试图用**串形态**区分「手误」与
「合法简拼/混拼」。这条路走不通，因为两者在字形上高度同形：

| 输入 | 是手误吗 | 能切成什么 |
|---|---|---|
| `nihap` | 是（想打 nihao） | `ni + ha + p`（有完整音节） |
| `chifanl` | 否（吃饭 + l） | `chifan + l`（有完整音节） |
| `zhogn` | 是（想打 zhong） | `z + h? + o + g? + n?`（全是碎片） |

正确做法是**双层设计**：
1. 预筛只用形态做**保守排除**（能切成「完整音节 + 声母」的一律信任），
   目的是省开销，不是做最终判断；
2. 是否让纠错候选领跑，由**词典事实**决定：纠错命中的词频必须 ≥ 常规单词级
   候选最高词频的若干倍（本项目取 2，见 `typoPromoteRatio`）。

实测直接放开（纠错候选无条件置顶）的代价：合法混拼首选率 34.32% → 20.75%，
且 `zhongg` → 中国 这类既有用例直接失败。

另一个必须避开的坑：比较「常规候选有多强」时**只能用单词级精确匹配**
（rankExact / rankInitialExact）。DP 拼接候选的 Score 含「多字词奖励
(l-1)*100」，`zhogn` 的碎片拼接「中欧个」能到 265 分，而真实高频单字
「中」只有 90——用 Score 或含拼接候选做门槛，纠错会被永远挡住。

### 陷阱 5：纠错生成的性能陷阱（毫秒级延迟）

单次编辑会产生上百个修正串。两个开销必须分开控制：

- **生成便宜**（纯音节 DP 校验，实测约 39µs）；
- **每条一次的词典 Trie 查询很贵**（160 条约 2ms，实测 `zhonguo` 从 0.8µs
  涨到 25ms）。

因此：① 修正串只取**首条切分**，不枚举全部歧义路径；② 实际查询条数用独立
常量封顶（`typoMaxQueries`），不要让它等于生成上限。另外生成时的候选过滤
要用**纯音节 DP**（`hasCleanSyllableSplit`），不能用完整预筛——后者内部还会
做一次切分，而上限外的前几千条候选都会被白跑一遍。

### 陷阱 6：学习到的整句变成「整词贪婪匹配」

用户 2026-10-30 明确要求：学过「今天星期一」后，打「今」不能直接给候选
「天星期一」；否则用户这次只想打「今天」时会被整词候选/联想尾巴挤掉，
之前的输入习惯反而变成负资产。

实测（HEAD b4785e6，改动前）：
- 整句候选一键上屏 → `BumpWord` 把任意长整句写进 Words（无长度上限），
  打 `jin` 时整句排在「今天」之前（#59 vs #62），上屏「今」的联想首条
  直接是「天星期一」（score 500，第 2 条才是「天」70）；
- 尾巴还能被 `AssociateSelect` 再学习：之后 `tian` 下「天星期一」#40
  反超「天气」#46，形成污染循环；
- 5 音节以上组合原本完全学不到（`maxLearnSylls=4` 只约束 Phrases 表）。

正确做法（`engine/sequence_learn.go`）：
1. 学习记录带**分段**：整句 `今天星期一` → `Segs=[今天,星期一]`；
2. 整句候选**只在完整输入**时参与（部分输入的前缀层过滤整句式记录，
   `isSentenceEntry`）；
3. 联想剥前缀只允许在**分段边界**（`stripAtSegmentBoundary`）：今天→星期一 ✓、
   今→天星期一 ✗；普通词典词/词组进化的行为不变；
4. 「一键整句上屏」按逐段确认的等价路径学习分段词，与逐段选择落同一套数据；
5. 旧数据没有 Segs 时用主词典最长词切分推断边界，推断不出按普通词处理。

回归测试必须双向（`engine/sequence_learn_test.go`）：正向证明完整输入时
学到的整句确实被加权、分段边界续接仍在，反向证明部分输入/联想不出现整词
尾巴且「今天」首选不受影响。只测正向的话，「有整句记录就无条件置顶」这种
粗暴实现也能通过。

## 三、参数扫描纪律

任何引入的经验参数（惩罚系数、阈值）都必须：

1. 在**完整基线数据**上扫描至少 4–5 个取值，把每个取值的关键指标记下来；
2. 选值要有明确理由：本项目 `continuationPenalty = 30` 是唯一同时保住
   「full.top1 不降」与「tail1.top1 最大」的点（20 侵蚀完整输入，40 收益缩水）；
3. 把扫描结论写进代码注释与 README，不留在对话里——否则下次有人「顺手调一下」
   就会破坏平衡且无人知道边界在哪。

## 四、改动后的验证清单

```sh
gofmt -l engine/ cmd/ ipc/ skin/
go vet ./...
go test ./... -count=1
go test -race -count=1 ./engine/
make build
# 关键路径性能不能明显退化（本项目基准为微秒级）
go test ./engine/ -run '^$' -bench 'ComposeCommonDict' -benchtime 20x -count=3
```

性能数据必须多次采样对比（`-count=3`），单次结果在 M1 上有 ±10% 抖动，
容易把噪声判成回归。

## 五、回归测试要守住的两个方向

新增排序/匹配能力时，测试必须**双向**覆盖，缺一不可：

- **正向**：新能力真的生效（`zhonggu` → 中国、`quanmia` → 全面）；
- **反向**：不反噬既有行为（`yisha` → 一霎、`nihao` → 你好、`jingchang` → 经常）。
  只写正向测试的话，「把所有预测候选置顶」这种粗暴实现也能通过。

见 `engine/continuation_test.go` 的三段式结构（预测生效 / 不反噬完整输入 / 常用词守门）。
